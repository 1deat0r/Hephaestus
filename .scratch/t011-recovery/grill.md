## Round 1

❓ **Q1 Scope**: in — an `operations` module: durable **operation records**
(id, task, attempt, lifecycle state) whose lifecycle transitions are events
appended to the T-006 `EventLedger` **before** the corresponding side
effect; **effect receipts** (outcome + cost + wall-time + reason) as events;
**replay** that rebuilds per-operation state from the ledger alone; a
**recovery plan** (requeue / ambiguous→budget-reconcile / terminal) applying
AT-057's "retries only permitted"; **fault-injection tests** at the four
plan boundaries via the reopen-from-disk pattern. Out: distributed
consensus, multi-writer journals, checkpoint files beyond what the ledger
already is, provider-side idempotency-key negotiation with real externals
(the *hooks* exist, real externals arrive with providers).
*source: plan text + :369/:371/:377.*

❓ **Q2 Location**: `crates/hephaestus/src/operations/` — spans ledger,
budget and scheduler, so it sits beside them (same one-module-per-interface
discipline); MASTER_SPEC's TraceExporter/ExecutionBackend names don't fit
better.
*source: house pattern.*

❓ **Q3 Durability mechanism**: `OperationRecorder` owns a path to an
`EventLedger`. Every transition appends an `event` contract record
(`event_type` strings: `operation.planned`, `operation.dispatched`,
`operation.receipt`, `operation.cancel_requested`, `operation.output_committed`,
`operation.reconciled`; `operation_id` field = our op id; `sequence` per
mission id `OPS`). Append-before-effect: recorder's API returns only after
`sync_data` succeeds; callers then act. Receipts carry a JSON payload hashed
into `payload_sha256` **whose bytes are staged into the ledger's… no —
payload bytes live in an `ArtifactStore`?** Simpler M1: receipt facts go in
the event's `event_type`+`subject_ref`+`operation_id`… that loses cost/reason
data. Decision: keep receipts as **events whose payload JSON is stored in
the T-006 ArtifactStore** and referenced by `payload_sha256` (closes the
artifact-integration deferral too); replay reads receipts via store+hash.
Runner-up — inline payload in a ledger sidecar — rejected: hash chain
already covers the event; store is content-addressed for exactly this.
*source: contracts event schema (payload_sha256) + T-006 design.*

❓ **Q4 Operation identity & state machine**: `OperationId` = caller string
or generated `OP-<seq>`? → generated by recorder (monotonic per ledger run +
caller tag), unique, durable at `planned`. States (derived, never stored as
truth): `Planned → Dispatched → {Succeeded, Failed, TimedOut, Cancelled,
Ambiguous}`; `CancelRequested` is a flag event. State = replay(events) only;
no second store (single source of truth = ledger).
*source: :369 + T-006 single-authority pattern.*

❓ **Q5 Replay rules**: scan ledger in chain order, fold per-op; **validate
chain first** (T-006 open does); order violations (receipt without
dispatch) ⇒ that op → `Corrupt` (fail-closed, reported, never auto-fixed);
missing receipt after dispatch ⇒ `Ambiguous`. Rebuild returns
`OperationLedgerView { states, receipts }` + deterministic iteration order
(declaration order = ledger order).
*source: AT-057 + determinism discipline.*

❓ **Q6 Recovery plan**: `recover(view, budget, dag) -> RecoveryPlan`:
- `Succeeded/Failed(final)/TimedOut(final)/Cancelled` ⇒ terminal, no action.
- `Ambiguous` (dispatched, no receipt): **release any still-held reservation
  and `mark_unresolved(op_id, Some(cost), "no receipt after dispatch")` if
  non-idempotent (`retryable: false`); if retryable ⇒ still NOT blind:
  requeue only when `attempts < max_attempts` (AT-057 "retries only
  permitted"), else unresolved. Wait — retryable+exhausted ⇒ Failed.
- `Planned` (never dispatched) ⇒ requeue (nothing happened — safe).
- `Corrupt` ⇒ excluded from requeue, surfaced for operator.
Plan output: `requeue: Vec<OperationId>`, `unresolved: Vec<…>`,
`terminal: …`, `corrupt: …`. Applying a plan = building a fresh Scheduler
over the DAG subset (M1: caller re-runs; module provides the plan, not the
rescheduling loop — scheduler already owns dispatch).
*source: AT-057 + MASTER_SPEC:371 + T-008 API.*

❓ **Q7 Receipt contents**: exit outcome variant, cost (Money), wall_ms,
failure reason, attempt #, executor name (opaque string), artifact hashes
(may be empty). Serialized JSON → ArtifactStore commit → event appended
with `payload_sha256`. Crash between store-commit and event ⇒ orphan
artifact (retained per T-006) + op stays Ambiguous ⇒ recovery marks
unresolved — **not** a blind retry (exactly the plan's "before output
commit" boundary semantics: nothing claims completion).
*source: T-006 orphan decision + :371.*

❓ **Q8 The four fault boundaries** (test design, reopen-from-disk pattern
from T-006):
1. **before dispatch**: `planned` appended, crash → replay: Planned →
   requeue; budget untouched.
2. **after dispatch**: `dispatched` appended, crash before receipt →
   Ambiguous → recovery: release reservation (if held) + unresolved (or
   requeue-if-retryable per Q6) — never auto-success.
3. **before output commit**: receipt NOT appended, artifact store commit
   happened (test uses ArtifactStore directly) → replay still Ambiguous
   (events rule); orphan artifact retained; plan marks unresolved.
4. **after external effect**: executor returned AmbiguousEffect, crash
   before `reconciled` event → replay Ambiguous → recovery calls
   `mark_unresolved` exactly once (idempotent guard: if an
   `operation.unresolved` event already exists, skip — AT-056 discipline).
   Plus **during cancellation**: `cancel_requested` appended, crash before
   flag set → replay: treat as CancelRequested → plan cancels (no dispatch)
   rather than requeue.
*source: plan sentence + T-006 fault pattern.*

❓ **Q9 Concurrency/writer model**: single in-process writer, recorder
`&mut self` (same class as T-006/T-008); no locking needed for M1.
*source: :379 one authoritative writer.*

❓ **Q10 Interaction with Scheduler/SandboxExecutor**: no changes to either
— the recorder **wraps** execution at the caller seam: tests (and later the
gateway) do `planned → dispatch via scheduler with a RecordingExecutor
decorator → receipt`. Design: `RecordingExecutor<E: TaskExecutor>` decorator
implements TaskExecutor: `planned` must be appended by the caller before
`run` (or decorator's `run` appends `dispatched` first thing, caller appends
`planned` when building the DAG run) — decorator appends `dispatched`
**before** delegating (append-before-effect ✓) and appends `receipt` after
(with store commit when outputs present). Cancel: `recorder.cancel(id)`
appends `cancel_requested` then flips the scheduler handle.
*source: capability-contract discipline (no scheduler edits).*
